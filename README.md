# VFS: Busy inodes after unmount of a nilfs2 mount (kernel BUG at fs/super.c:731)

Syzkaller-found bug on Linux v7.4-rc2, reproduced and verified on the same
kernel build. Reproduces on a freshly booted VM in ~1-2 minutes with a single
self-contained test program. A C reproducer (`reproducer/repro.cprog`) is also
provided and was verified: compiled with `gcc -O1 -static` and executed
directly in a fresh VM it panics the kernel at fs/super.c:731 in ~114 seconds
(including guest boot); see `logs/c-verification/`.

## Summary

On unmount of a nilfs2 filesystem, `generic_shutdown_super()` finds inodes
still present on the superblock's inode list:

```
NILFS (loop5): disposed unprocessed dirty file(s) when stopping log writer
VFS: Busy inodes after unmount of loop5 (nilfs2)
------------[ cut here ]------------
kernel BUG at fs/super.c:731!
Oops: invalid opcode: 0000 [#1] SMP KASAN NOPTI
CPU: 3 UID: 0 PID: 10340 Comm: syz-executor Not tainted 7.4.0-rc2-kernsight-kasan #1 PREEMPT(full)
RIP: 0010:generic_shutdown_super+0x305/0x3a0 fs/super.c:731
Call Trace:
 kill_block_super+0x49/0x130 fs/super.c:1852
 deactivate_locked_super+0xc0/0x130 fs/super.c:558
 deactivate_super+0xb9/0xd0 fs/super.c:582
 cleanup_mnt+0xbc/0x160 fs/namespace.c:1396
```

The `CHECK_DATA_CORRUPTION(... "VFS: Busy inodes after unmount of %s (%s)")`
in `generic_shutdown_super()` (fs/super.c:731) fires, which with
`panic_on_warn=1` escalates to a kernel BUG/panic. Residual busy inodes after
unmount means subsequent accesses can touch a freed superblock/inode
(use-after-free class), which is why syzkaller titles this report
"VFS: Busy inodes after unmount (use-after-free)".

Just before the failure the nilfs2 log writer reports:

```
NILFS (loop5): disposed unprocessed dirty file(s) when stopping log writer
```

i.e. `nilfs2` disposes unprocessed dirty files while stopping the log writer
(`nilfs_detach_log_writer()`), leaving inodes on the superblock inode list at
the time VFS checks them in `generic_shutdown_super()`. The interplay between
the nilfs2 log writer shutdown path and the VFS unmount cleanup appears to
violate the "no busy inodes after unmount" invariant.

## How to reproduce

Environment used: Debian trixie x86_64 guest (6 GiB RAM, 4 vCPU, KVM),
kernel built from v7.4-rc2 with CONFIG_KASAN=y, CONFIG_PROVE_LOCKING=y
(CONFIG_NILFS2_FS=y), booted with `panic_on_warn=1`.

Two equivalent reproducers are provided:

C reproducer (verified):

```sh
# on the host:
gcc -O1 -static -o repro reproducer/repro.cprog
# copy `repro` into the guest and run it as root:
./repro
```

syz reproducer:

```sh
# in the guest, as root:
syz-execprog -procs=1 -threaded -repeat=0 -executor ./syz-executor repro.prog
```

On a freshly booted VM the kernel BUG at fs/super.c:731 fires within the
first ~1-2 minutes of execution (verified repeatedly on fresh VMs; see
`logs/crash-serial-excerpt.txt` and `logs/c-verification/` for console logs
recorded during verification runs).

`reproducer/repro.prog` is a single self-contained syzkaller program: it
mounts a crafted nilfs2 image (`syz_mount_image$nilfs2`), creates a file and
issues `NILFS_IOCTL_CLEAN_SEGMENTS` on it. The crash surfaces when the
syzkaller executor tears down its per-run working directory (forced
`umount2(..., MNT_FORCE)`) while the broken, read-only nilfs2 mount still
has dirty inodes. `reproducer/repro.cprog` (generated by syzkaller's
reproducer pipeline and verified by running the compiled binary in a fresh
VM) performs the same sequence, including the forced-unmount teardown, and
reproduces the same BUG.

## Notes for maintainers

- The crash is in the VFS invariant check, but the state that violates it is
  produced by the nilfs2 log writer shutdown path, so we are reporting to the
  nilfs2 list first (fs/super.c/cc VFS in the loop).
- Same-family reports from the same campaign on this kernel also include a
  jfs `BUG_ON(!list_empty(&ji->anon_inode_list))` in `jfs_evict_inode()`
  during `generic_shutdown_super()`; they are reported separately.
